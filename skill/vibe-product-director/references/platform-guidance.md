# Platform Guidance

当产品平台会改变交互、技术、分发、审核、账号、支付、性能或验收时读取。会变化的规则必须查平台官方资料并记录检索日期；本文件只提供决策维度，不固化易变限制。

## 营销网站

重点判断：搜索与社交发现、首屏价值表达、内容层级、转化路径、表单/线索、CMS、分析与同意管理、图像/字体/脚本预算、可访问性和移动网络。

不要把营销站设计成登录后工具工作台，也不要为了“炫酷”牺牲 LCP、可读性和主 CTA。

## Web App / React 应用

重点判断：公开内容是否需要 SEO/SSR、登录边界、路由与深链、高频键盘操作、响应式工作区、状态同步、离线/弱网、浏览器支持、缓存和前后端错误恢复。

用户提到 React 是偏好或约束，不自动决定渲染模式、后端、数据库和部署。

## 移动 App

重点判断：平台原生能力、手势与系统导航、权限申请时机、推送、后台任务、离线、深链、应用商店审核、升级兼容、崩溃/性能、触觉反馈和小屏任务重排。

移动端不是桌面页面缩小版。明确哪些任务优先、哪些延后、哪些用系统组件。

## 桌面应用

重点判断：窗口/多窗口、菜单、快捷键、文件系统、拖放、托盘、自动更新、系统权限、本地数据、离线、跨平台差异和签名分发。

## 小程序

重点判断：平台登录与用户标识、授权时机、支付/分享/订阅消息、包体和分包、页面栈、WebView 边界、审核规范、隐私声明、域名/证书、文件与存储限制、性能和版本发布。

登录、支付、分享和隐私规则必须查对应平台最新官方资料；不要把网页 OAuth 或浏览器行为机械搬入小程序。

## 多端产品

先定义共享的领域规则、身份、核心实体和 API，再定义各端不同的任务优先级、导航、输入方式、能力和发布节奏。不要追求所有端功能完全相同。

创建 `PLATFORM_CONSTRAINTS.md`，记录：平台、约束证据、影响的 `DEC/ACT`、端内行为、替代/降级、测试设备和审核/发布 owner。

## 技术选择

技术架构晚于产品、体验和系统驱动因素。给出主方案和一个真实备选，比较实现复杂度、团队能力、锁定/迁移、成本、性能和运维；说明为什么不选常见方案。优先选择满足当前需求的最简单方案，并保留可验证的迁移路径。
