# Product Scope and Risk

在讨论产品价值、角色、范围、功能、运营、商业化或产品风险时读取。

## 1. 第一性原理链

每项重要内容都应能追溯：

```text
用户问题 → 希望发生的行为变化 → 核心任务 → 必要能力
→ 页面与交互 → 业务规则与数据 → 技术能力 → 验收证据
```

无法说明服务哪个用户结果的功能、页面、角色、技术层或文档，进入质疑或删除队列。

项目锚点至少包含：第一优先用户、具体场景、要解决的问题、用户可见结果、首发平台和硬约束。成功不是“上线”，而是可观察的用户或业务结果。

## 2. 苏格拉底式追问

只在答案会改变范围、体验、风险、架构或验收时追问：

- 什么证据说明用户会这样做？当前替代方案具体哪里失败？
- 删除该功能后，核心价值是否仍成立？
- 哪个角色会因这个决定受损？谁承担运营或审核责任？
- 什么情况下方案会失败，用户如何恢复？
- 用户说“炫酷”时要的是冲击、品牌、沉浸、可信度还是展示效果？
- 用户说“功能丰富”时要的是任务闭环还是入口数量？
- 是否存在更简单的方式实现同一用户结果？

不要无限追问“为什么”。用户已给出足够行为结果后关闭分支。

## 3. 发散与收敛

需要创意时先发散真正不同的方向，可改变定位、入口、主交互载体、信息架构、运营、社交、商业模式或媒介；不要只换文案和颜色。

收敛依据：用户价值、易用性、辨识度、实现成本、性能、风险、上线时间、扩展性和用户偏好。保留推荐及真实备选，不保留无胜算的陪跑方案。

## 4. 功能组合

按旅程选择适用层，不机械补齐：

- **Core**：没有就不能完成核心任务。
- **Expected**：品类用户自然期待且缺失会显著损害可用性。
- **Trust**：身份、权限、可信信息、确认和安全感。
- **Recovery**：草稿、撤销、找回、失败重试、申诉和帮助。
- **Operations**：管理员、审核、配置、客服、风控和数据。
- **Delight**：可衡量地提高成功率、效率或品牌记忆。
- **Growth**：分享、邀请、回流、留存和传播。
- **Expansion**：有合理预期但不应现在构建的扩展。
- **Reject**：与目标冲突或成本/风险不成比例。

每个 Must/Should 候选至少说明：用户问题、角色、旅程位置、收益、不做后果、复杂度、依赖、风险、衡量方式、优先级和进入/退出 MVP 的理由。

## 5. 旅程完整性

对每个核心角色覆盖：触发与入口、前置条件、发现/比较、执行、系统处理、成功结果、后续复用、失败恢复、通知/协作、运营介入和度量。

按需检查：首次使用、重复使用、回流、onboarding、搜索、表单、草稿/自动保存、批量、空/加载/弱网/离线/超时、无权限、冲突、撤销、删除恢复、通知、分享、举报、审核、客服、后台、配置、分析、滥用、平台审核和无障碍。

## 6. Remove-One 与扩展边界

每次 MVP 收敛都回答：若必须再删一个功能，删什么，核心价值是否仍成立？

有明确预算、期限或团队容量时，重复 Remove-One 并同步缩小首个纵向切片，直到估算与容量证据相容。若仍超限，不得因“已经删过一个”而停止；若缺少会影响交付承诺的容量事实，将其列为 Blocking。

现在只预留会避免高成本返工的稳定边界：角色/权限模型、核心实体状态机、必要外部 ID、集成边界、关键事件、审计和迁移路径。

延后：无真实场景的微服务、复杂消息总线、假想多租户、无证据的推荐/社交/AI、未确定市场的完整国际化。

## 7. Red-Team 检查

尝试证明当前方案错误：

- 用户是否其实不需要产品，或核心功能只是看起来有用？
- 哪一步最可能放弃、误解或失去信任？
- 多角色目标是否冲突，谁优先？
- MVP 是否包含多个半成品旅程？
- 运营、审核、客服、退款或恢复是否被假定为“系统自动解决”？
- 建议功能是否增加维护与运营负担但没有衡量收益？

只把会改变决定的结论写入风险、范围或验收，不输出一份重复的角色独白。
