# Decision Evidence and Prototyping

在项目高歧义、Deep 模式、决定依赖复杂、需要外部知情人、需要比较高锁定接口，或用户请求先做原型验证时读取。

## 1. Destination、决定图与迷雾区

先写 Destination：完成后谁在什么场景下能产生什么可观察结果，以及哪些硬约束不得破坏。它是方向，不是功能清单。

Decision Map 只做索引：

```text
Decision | Status | depends_on | blocks | authority | next evidence
```

- 节点是需要关闭的决定，不是开发任务或文档章节。
- 边表示“没有上游结论就不能可靠决定下游”，不要用时间顺序伪造依赖。
- `Frontier` 是依赖已满足、证据足够形成决策简报的节点。
- `Fog` 是已知重要、但当前还不能准确命名选项或问题的区域；先探索证据，不强迫用户回答模糊问题。
- 每个决定只有一个权威位置；Map 使用链接和一行状态，不储存完整结论。

项目简单时不绘制大图，只在 `PROJECT_STATE.md` 保留当前 frontier。复杂项目只展开足以看到下一批解锁关系的局部图，不预先规划全部未来。

## 2. 决策就绪简报

向用户提出高影响取舍前，先准备：

1. **要决定什么**：一句话和为什么现在必须决定。
2. **已知事实**：来自环境、现有产品、代码、设计、用户或一手资料。
3. **仍未知什么**：未知若错误会造成什么影响。
4. **真实选项**：2–4 个会改变结果的方案，不放陪跑项。
5. **推荐**：依据、代价、可逆性和重开条件。
6. **用户只需做什么**：选择、授权或完成 Agent 无法代做的人工步骤。

事实查找是 Agent 的工作；价值取舍和授权是用户的工作。能通过文件、运行环境、官方资料、可观察产品或低成本实验得到的事实，先自行完成。

## 3. 最小证据阶梯

从成本最低、最能改变决定的方法开始：

1. 读取现有文件、数据、页面、日志、测试和历史决定。
2. 查官方/一手资料；逐项记录来源、日期、结论与影响的 `DEC/OPEN/RISK`。
3. 比较现有产品、真实工作流或同类交互，记录行为证据而非只截视觉风格。
4. 向真正掌握信息的人收集定向答案。
5. 制作隔离的证据原型或高锁定接口备选。

研究开始前先写它要改变哪个决定；新资料已不能改变选项或推荐时停止。不得把搜索摘要当权威来源，也不得为了显得充分而累积无决策价值的材料。

## 4. 利益相关者问卷

只有当关键知识确实存在于运营、销售、客服、法务、财务、领域专家或真实用户脑中，且 Agent 无法从现有证据可靠推断时，才创建 `STAKEHOLDER_QUESTIONNAIRE.md`。

围绕“收到答案后要关闭哪些决定”来设计问卷：

- 写明收件角色、背景、涉及 `DEC/OPEN`、截止点和答案会阻塞什么。
- 每个问题指向一个待关闭知识缺口；删除只满足好奇心的问题。
- 允许“不知道/需转交”，并要求具体例子、异常案例或现行规则。
- 收到回答后抽取事实、矛盾和决定影响；问卷本身不是最终产品权威。

## 5. 证据原型

原型用于回答决定，不用于偷跑生产开发。开始前必须满足：

- 明确一个问题、成功/失败判据、owner 和将影响的决定。
- 获得用户对“制作非生产原型”的授权。
- 放在 `product-blueprint/prototypes/`、`docs/product-blueprint/prototypes/` 或系统临时目录；不得无声修改生产路由、组件、数据库或接口。
- 标记为 throwaway，禁止复制未经审查的原型实现进入生产。

### 逻辑/状态原型

适合验证状态机、权限、计算、冲突、异步恢复或复杂交互规则。使用最小可运行模拟，包含自由操作和刻意尴尬的边界场景；状态转换必须可观察。若静态表格或测试示例已足够，不写代码。

### 界面/流程原型

适合验证信息架构、主交互载体、密度、导航或关键流程。比较方案时给出 2–3 个结构上真正不同的方向，并让相同任务可切换比较；不要只换颜色。覆盖正常、空、错误、长内容、窄屏和关键可访问路径。

原型结束后记录：

```text
Question → Artifact/location → Scenarios → Observation
→ Decision impact → Adopt/Reject/Needs evidence → Disposal plan
```

只有观察与结论进入 `DECISIONS.md`、相关权威蓝图和验收；原型不自动成为规范。

## 6. 高锁定接口：Design It Twice

当模块边界、平台适配层、跨端共享契约、第三方抽象或核心状态接口难以逆转时，独立设计两个能成立的方案，再比较：

- 调用者需要知道多少内部细节。
- 是否形成“深模块”：接口窄而能力完整。
- 能否通过公开 seam 测试行为，而不是锁死内部实现。
- 错误、取消、超时、版本和迁移如何暴露。
- 当前是否真的有两个适配器，或只有一个真实适配器加一个明确的近期证据。

不要为普通 CRUD 或可逆 UI 细节做双方案。抽象通常在两个真实用例出现后建立；若现在只有一个，保留清晰 seam 和替换路径，不购买假想扩展性。

## 7. 阶段边界与人工门

一个决定簇尚未闭合时，不切换到无关研究、原型或开发。切换前：

1. 更新 `PROJECT_STATE.md`、决定状态、fog/frontier 和下一最小行动。
2. 把已闭合结论写入唯一权威文档，保存证据链接与重开条件。
3. 标明新阶段的入口条件、出口证据和停止条件。

Agent 无法代办的账号开通、合同、法务批准、支付主体认证、真实用户访谈或设备操作写成 Human Gate：`owner / exact action / evidence returned / blocks / deadline or trigger / irreversible confirmation`。先把 Agent 可完成的准备工作做到最远，再交给用户。

## 8. 关闭证据循环

证据完成后只允许三种结果：

- **Close**：决定可关闭，写入理由、影响、可逆性和重开条件。
- **Narrow**：缩小选项或拆出新的、可准确提问的 frontier。
- **Stop**：证据成本超过决定价值；使用可接受默认，或将真实风险标为 Blocking/Conditional/Later。

不允许“做了研究/原型但没有改变任何状态”。每项证据资产必须链接到决定、风险、验收或明确的废弃结论。
